Contract-First Multi-Platform Component Handoff
Part 1 · The case
    Architecture Proposal

    Contract-First Multi-Platform Component Handoff

    Define a component once, in a platform-neutral contract. The design system owns every design decision; platform teams own translation — and are free to be native wherever it doesn’t change how the component looks or behaves.

    Status  Draft for review Owner  Design Systems Reviewers  Web · iOS · Android leads

    In short

    1. The betThe design system resolves every design decision into a per-platform artifact. Platform teams translate it. Nobody re-derives intent from a screenshot.
    2. The boundaryDS owns semantics — the cascade, the spring math, the a11y mapping. Teams own syntax — the SwiftUI and Compose code. Neither side does the other’s job.
    3. Native by defaultFields are either resolved (one value, no discretion) or adaptable (platform picks the mechanism inside a declared envelope). Adaptable fields ship with a working fallback, so they permit a decision — never require one.
    4. The gateContracts are reviewed by web, iOS, and Android leads before implementation. Conformance assertions — exact on invariants, bounded on adaptables — then block merge.
    5. The costContract authoring is real work: 400–700 lines for a component with full behaviour and motion. This is not free and should not be sold as free.

    The problem we’re solving

    Today a component ships on web first. A screenshot, a Figma link, and a Storybook URL go to the iOS and Android teams. Each team independently reconstructs the component’s intent from artifacts that were never designed to carry it.

    Three teams infer. Three teams guess differently. The divergence isn’t caught in review — it’s caught in QA, or by a user.

    What handoff losesHow it surfaces
    Prop semantics & namingThree different APIs for one component; call sites aren’t portable and docs fork
    State coverageA state exists on web and silently doesn’t on Android. Nobody notices until a designer opens the build
    Motion feelDurations get copied, curves get eyeballed, springs get re-tuned by hand and read differently per platform
    Accessibility intentARIA is web-shaped, so it doesn’t translate. Native a11y gets reinvented per component, inconsistently
    Token bindingsA hardcoded hex creeps into one platform. The rebrand ships broken on exactly one target
    Interaction logicHover has no touch equivalent. Each team invents its own mapping and they don’t agree

    After: one contract, reviewed by all three platforms before anyone writes code, resolved into a per-platform artifact where the design decisions are already made. Drift stops being a discovery and becomes a red build.

    The shape

    The contract is the hub. Tokens are referenced from the existing library — never rebuilt here. The tool stops at the resolved artifact; teams take it from there.

    The boundary

    Everything rests on one line being drawn correctly and then held. Cross it and platform teams reject the output; stop short of it and drift returns.

    Design system owns — semantics

    Every design decision · resolved before handoff

    • Cascade resolution — variant × size × state flattened
    • Token paths resolved to platform symbols
    • Spring and easing conversion per platform
    • Prop naming and support mapping
    • State applicability — which states exist where
    • Accessibility intent → platform semantics
    • Layout intent — direction, order, alignment, sizing
    • Adaptability envelopes and their fallbacks

    Platform teams own — syntax

    Translation · plus bounded native latitude

    • A thin generator reading the resolved artifact
    • The SwiftUI view body / the Composable body
    • Layout mechanism — HStack, Row, flexbox
    • Native mechanisms inside declared envelopes
    • One conformance runner adapter, written once
    • Framework choice — Compose or Views, SwiftUI or UIKit

    Native by default, within an envelope

    “No design decisions for teams” and “let platforms feel native” only conflict if fields are left ambiguous. They are reconciled by classifying every field into one of exactly two tiers.

    TierMeaningTeam latitude
    ResolvedOne explicit value. Defines what makes the component recognisably itselfNone — transcribe it
    AdaptableIntent + constraint envelope + a working fallbackMay substitute a native mechanism inside the envelope

    There is no third category. A field that is neither is a bug, and --strict fails the build over it.

    The property that makes this work

    Every adaptable field ships with a fallback that is already correct. A team that wants to ship without thinking about it simply uses the fallback and gets a compliant component. Adaptable fields therefore permit a platform decision — they never require one. That is what keeps “teams don’t make design decisions” true while still allowing native character.

    Sequencing

    Dependency-ordered stages. Stage 0 → 1 is the critical path; most of what follows parallelizes across platforms.

    1. Lock decisionsUnblocks — everything

      Token library path, per-platform symbol naming, and who co-authors each completeness schema.

    2. Contract schema + validatorUnblocks — all resolution

      The highest-value artifact. Author it with native engineers in the room, not after.

    3. Resolver + completeness schemasUnblocks — platform work

      Cascade flattening, curve conversion, intent mapping, tier classification. This is the semantic core.

    4. Conformance assertions + runner adaptersMakes the contract binding

      DS emits assertions as data; each platform writes one runner. Until this lands, the contract is documentation.

    5. Pilot two components end to endValidates the schema

      One simple, one behavioural. Ship both on web, iOS, and Android before writing a third contract.

    6. Roll out remaining componentsScales the system

      Only after the pilot has survived contact with all three platform teams.

    No calendar estimates — deliberately

    Stage ordering is a technical fact; duration is not. Real week numbers need headcount, how contended the iOS and Android teams are, and whether the token library already exposes native symbols. Ask for those and the estimate becomes defensible — without them it is a number invented to be presented.

    Definition of done

    Observable criteria, not milestones. The system is working when all seven hold:

    • Two components ship on web, iOS, and Android from a single contract
    • resolve --strict passes for every platform — no unclassified or unresolved fields
    • Conformance assertions gate merge in all three platform repositories
    • A contract change automatically opens PRs on every platform repo with a readable changelog
    • At least one platform has used an adaptable envelope to ship something more native — and still passes conformance
    • A drift dashboard shows every platform on the same contract major version
    • A native engineer has rejected or amended a contract in review — proof the gate is real, not ceremonial
    The two that actually matter

    The last criterion tests whether the review gate is real. If no contract is ever pushed back on by iOS or Android, the review is theatre and the contract is quietly web-shaped — reproducing the original problem with more machinery around it. The fifth tests the opposite failure: if no team ever exercises an envelope, the adaptability model is dead weight and should be simplified away.

    Phase 1 — The contract schema

    Seven blocks. This is the only thing authored by hand.

    1.1  props — full API surface

    Distinguish prop kinds, not just types. Each carries platform disposition and naming.

    "props": {
  "variant": {
    "kind": "enum", "values": ["primary", "secondary", "ghost", "destructive"],
    "default": "primary", "axis": true
  },
  "size": { "kind": "enum", "values": ["sm", "md", "lg"], "default": "md", "axis": true },

  "label": {
    "kind": "string", "required": true,
    "constraints": { "nonEmpty": true, "maxLength": 40 },
    "a11y": { "usedAsAccessibleName": true }
  },

  "onPress": {
    "kind": "event", "payload": "none",
    "names": { "web": "onClick", "ios": "action", "android": "onClick" }
  },

  "iconStart": {
    "kind": "slot", "contentType": "icon", "required": false,
    "names": { "ios": "leadingIcon", "android": "leadingIcon" }
  },

  "fullWidth": {
    "kind": "boolean", "default": false,
    "platforms": {
      "web":     { "supported": true },
      "ios":     { "supported": false, "as": "modifier", "note": ".frame(maxWidth: .infinity) at call site" },
      "android": { "supported": false, "as": "modifier", "note": "Modifier.fillMaxWidth() at call site" }
    }
  }
}

    axis: true marks a prop as a variant axis — it drives the appearance matrix, the Figma variant set, and the resolved artifact’s axes.

    Controlled vs. uncontrolled state

    The single biggest API-shape divergence across platforms. Declare it explicitly rather than letting each team resolve it:

    "bindings": {
  "expanded": { "value": "expanded", "default": "defaultExpanded", "onChange": "onExpandedChange" }
}
    PlatformResolved shape
    Reactexpanded?: boolean + defaultExpanded?: boolean + onExpandedChange?: (b) => void
    SwiftUI@Binding var expanded: Bool
    Composeexpanded: Boolean, onExpandedChange: (Boolean) -> Unit (state hoisting)

    1.2  appearance — the token matrix

    States are deltas off default, so the matrix stays readable and the resolver flattens the cascade.

    "appearance": {
  "roles": ["fill", "label", "border", "focusRing"],
  "byVariant": {
    "primary": {
      "default":  { "fill": "{brand.500}", "label": "{neutral.0}", "border": "transparent" },
      "hover":    { "fill": "{brand.600}" },
      "pressed":  { "fill": "{brand.700}" },
      "disabled": { "fill": "{brand.200}", "label": "{neutral.400}" }
    }
  },
  "bySize": {
    "md": { "padX": "{space.md}", "padY": "{space.sm}", "gap": "{space.xs}",
            "fontSize": "{textSize.md}", "radius": "{radius.md}" }
  }
}

    1.3  layout — intent, not mechanism

    Layout is a design decision, so it belongs in the contract. The API used to achieve it is not, so it doesn’t.

    "layout": {
  "direction": "horizontal",
  "align": "center", "justify": "center",
  "childOrder": ["iconStart", "label", "iconEnd"],
  "sizing": { "width": "hug", "height": "hug" }
}

    Direction, order, alignment, and hug/fill behaviour are resolved. Whether that becomes an HStack, a Row, or a flex container is the platform’s business.

    1.4  behavior — interaction state machine

    Use an XState-compatible JSON subset so React consumes it literally, while Swift and Kotlin resolve to an explicit state list and transition table.

    "behavior": {
  "initial": "idle",
  "guards": { "interactive": "!props.disabled && !props.loading" },
  "states": {
    "idle": {
      "on": {
        "HOVER_IN": { "target": "hover", "platforms": ["web"] },
        "FOCUS":    { "target": "focused" },
        "PRESS":    { "target": "pressed", "guard": "interactive" }
      }
    },
    "pressed": {
      "entry": ["haptic:light"],
      "on": {
        "RELEASE_INSIDE":  { "target": "idle", "actions": ["emit:onPress"] },
        "RELEASE_OUTSIDE": { "target": "idle" }
      }
    },
    "loading": {
      "after": { "1000": { "actions": ["announce:loadingLabel"] } },
      "on": { "RESOLVE": "idle" }
    }
  }
}
    • "platforms": ["web"] on hover. Hover does not exist on touch. The resolver strips it from the iOS and Android artifacts entirely, so no team ever has to decide what to do with an inapplicable state.
    • haptic:light as an action. Native-only affordances are declared once and ignored by web, rather than invented ad hoc per platform.

    1.5  motion — animation specs

    "motion": {
  "transitions": [
    {
      "on": "idle->hover",
      "properties": ["fill"],
      "duration": "{duration.fast}",
      "curve": { "type": "cubicBezier", "value": [0.4, 0.0, 0.2, 1.0] },
      "interruptible": true,
      "reducedMotion": "instant"
    },
    {
      "on": "*->pressed",
      "properties": ["scale"],
      "to": { "scale": 0.97 },
      "curve": { "type": "spring", "stiffness": 400, "damping": 30, "mass": 1 },
      "reducedMotion": "instant"
    }
  ],
  "loops": [
    { "id": "spinner", "activeIn": ["loading"], "property": "rotation",
      "from": 0, "to": 360, "duration": 800, "curve": { "type": "linear" },
      "iterations": "infinite", "reducedMotion": "fade" }
  ]
}
    ContractWebSwiftUICompose
    duration: 200200msduration: 0.2durationMillis = 200
    cubicBezier [a,b,c,d]cubic-bezier(a,b,c,d).timingCurve(a,b,c,d, duration:)CubicBezierEasing(a,b,c,d)
    spring(stiffness, damping, mass)spring({stiffness, damping, mass}).interpolatingSpring(stiffness:damping:)spring(dampingRatio, stiffness)
    reducedMotion: instant@media (prefers-reduced-motion)UIAccessibility.isReduceMotionEnabledANIMATOR_DURATION_SCALE == 0
    • Canonical spring form is (stiffness, damping, mass). Compose needs dampingRatio = damping / (2√(stiffness · mass)); SwiftUI needs a comparable transform. Doing this in the resolver — once — is the only way these stay visually identical. This is where subtle bugs hide.
    • Restrict animatable properties to the cross-platform-safe set: opacity, scale, translateX/Y, rotation, and colour roles. Reject blur, boxShadow, and layout-driven width/height.
    • reducedMotion is required on every entry. Not optional — an accessibility requirement on all three platforms, and the field most often forgotten.

    1.7  adaptable — declared native latitude

    Where a native mechanism would read better than a literal one, declare the intent and the bounds rather than the implementation — and always supply a fallback.

    "adaptable": {
  "pressFeedback": {
    "intent": "immediate perceptible response on touch down",
    "preferred": "platformNative",
    "envelope": {
      "allowed": ["ripple", "highlight", "scale"],
      "maxDurationMs": 200,
      "mustPreserveLayout": true,
      "mustBePerceivable": true
    },
    "fallback": { "type": "scale", "to": 0.97 }
  },

  "loadingIndicator": {
    "intent": "indeterminate progress in place of the leading icon",
    "preferred": "platformNative",
    "envelope": {
      "sizeRange": [16, 20],
      "colorRole": "label",
      "position": "leading",
      "mustNotShiftLayout": true
    },
    "fallback": { "type": "rotatingArc", "durationMs": 800 }
  }
}

    Versioning is unchanged: "contractVersion": "1.0.0", where patch is docs only, minor adds an optional prop or a variant value, and major removes or renames a prop, changes a token binding, or changes behaviour, motion, or envelope semantics.

    Phase 2 — Resolve: the closed artifact

    The resolver is the semantic core and the only substantial thing the design system builds. Its output must be closed: every value a platform implementation needs is present, explicit, and singular. No nulls, no prose, no optional fields, no “see docs.”

    The test

    If a platform engineer reading the artifact has to think about what’s right, the artifact has a bug — not the engineer. Adaptable fields are the sole exception, and even they carry a fallback that is already correct.

    2.1  Where decisions leak

    These are the eight ways an artifact silently hands a design decision to a team. Each has a structural fix, and each fix is enforced by the completeness schema.

    LeakWhat the team is forced to decideHow it closes
    hover: supported: falseDoes pressed inherit hover’s styling, or is that state simply gone?State axis is pre-filtered per platform; the styles table covers exactly the listed states. Unsupported states never appear
    Unsupported prop with a prose noteReads English, picks a modifierProp is omitted from the artifact. Guidance moves to docs. The machine artifact carries zero prose
    "border": nullIs null “none” or “inherit”?No nulls, ever. borderColor plus borderWidth: 0
    Partial typographyfontSize given, lineHeight absent — team picksCompleteness schema requires every visual property the component declares
    Focus ringInset or outset? What width, what offset?Explicit focusRing: { color, width, offset, style }
    Touch target vs. natural heightPad the control, or expand the hit area invisibly?Explicit hitArea: { strategy, minPt }
    Loading compositionDoes the label stay? Where does the spinner go?Composition resolved per state — visible children enumerated in every style row
    Press feedbackRipple, scale, or platform default?Declared Adaptable with an envelope and a fallback — a recorded deferral, not a gap

    2.2  What’s invariant, what’s adaptable

    The dividing question is always: would changing this make it look or behave like a different component? If yes, it’s resolved. If no, it’s a candidate for native latitude.

    DomainResolvedAdaptable within envelope
    ColourRole → token binding per variant × state—
    Spacing & shapePadding, gap, radius—
    TypographyFamily, size, weight, line height—
    LayoutDirection, child order, alignment, hug/fillMechanism — HStack / Row / flex
    State coverageWhich states exist on this platform—
    AccessibilityRole, name source, state exposure, min target sizeAnnouncement delivery mechanics
    Motion timingDuration budget, reduced-motion fallbackCurve family — spring vs. timing, if it lands in budget
    Press feedbackPerceivable, ≤200 ms, layout-preservingRipple / highlight / scale

    ElevationPerceived depth levelShadow vs. Material elevation

    2.3  Enforcing closure

    contract-cli resolve --platform ios --strict
   // validates output against ios.completeness.schema.json
   // fails if ANY field is unresolved or unclassified
   // error names the contract field that must be added

    A gap in the contract becomes a build failure in the design system repo before it ever reaches a platform team. That is what converts “no design decisions” from an intention into a guarantee.

    The per-platform completeness schema is a first-class artifact — the formal definition of “what iOS needs to know”, co-authored once with the iOS lead and versioned alongside the contract schema.

    Phase 3 — Conformance and CI gates

    What turns the contract from documentation into a contract. The tool emits assertions as data; each platform writes one runner that maps assertion kinds onto its own test framework.

    { "assertions": [
  { "kind": "enumExact",      "target": "ButtonVariant",
    "values": ["primary","secondary","ghost","destructive"] },

  { "kind": "styleEquals",    "args": ["primary","md","idle"],
    "field": "fill", "expect": "DSTokens.brand500" },

  { "kind": "motionEquals",   "from": "*", "to": "pressed",
    "field": "dampingFraction", "expect": 0.75, "tolerance": 0.01 },

  { "kind": "minTouchTarget", "expect": 44 },

  { "kind": "envelopeBounded", "field": "pressFeedback",
    "maxDurationMs": 200, "mustPreserveLayout": true }
]}

    Assertions come in two flavours, mirroring the two tiers:

    • Exact assertions on resolved fields — equality, no tolerance beyond float epsilon.
    • Envelope assertions on adaptable fields — bounds, not equality. A team that ships a native ripple still passes, provided it completes inside 200 ms and doesn’t shift layout.

    The runner adapter is roughly 150 lines per platform, written once — not per component.

    SuiteWhat it asserts
    API conformanceEnum cases exactly match the resolved axes
    Token conformanceResolved style values match the artifact. Catches drift between token library and implementation
    Motion conformanceConverted curve parameters match. Catches the spring-conversion class of bug
    Envelope conformanceAdaptable substitutions stay inside their declared bounds
    A11y conformanceAccessibility audits, assertHasClickAction(), assertIsNotEnabled(), minimum touch target
    Behavioural scenariosShared scenarios — “given disabled, when tapped, onPress is not called”
    Visual snapshotsFull variant × size × state matrix, regression-gated within a platform only
    Do not pixel-diff across platforms

    Font rasterization, subpixel antialiasing, and text metrics differ irreconcilably between web, iOS, and Android — and adaptable fields mean the three are intentionally not identical. The cross-platform check is a human reviewing three matrices side by side. Automating it produces a permanently red build that everyone learns to ignore, which is worse than no check at all.

    Pipelines

    • DS repo: contract change → validate → resolve --strict for every platform → semver bump check → publish → auto-open PRs on each platform repo with the new artifact and a readable changelog.
    • Platform repos: contract-lock.json pins the version. CI fails if the artifact is stale or the pinned major lags. Conformance assertions run on every PR.
    • Drift dashboard: which platform implements which contract version — making lag visible rather than discovered.

    Phase 4 — Pilot, then roll out

    ComponentWhy it’s in the pilot
    ButtonHigh variant count, trivial composition, press feedback and a loading indicator — the two clearest adaptable fields. Proves the appearance matrix, the motion block, and the envelope model
    Accordion (or Select)Slots, expand/collapse, enter/exit transition, expanded binding, expanded-state a11y. Proves the state machine, controlled-state bindings, and a11y intent mapping

    One simple and one behavioural is the minimum that validates the schema. Do not write twenty contracts before one has shipped natively on both platforms.

    The process change that matters most

    1. Prototype in React (Storybook)         // fast, disposable
2. Write/update the contract              // ★ PR reviewed by web + iOS + Android leads
3. contract-cli validate && resolve --strict
4. Fan out: artifacts + assertions to each platform repo
5. Teams translate; conformance gates merge
6. Review the three builds side by side once

    Step 2 is the system. Native engineers reviewing the contract before implementation is where “hover doesn’t exist on iOS,” “that spring reads as sluggish in Compose,” and “this should use the platform ripple” get caught — at the cost of a code review instead of a re-implementation.

    Non-goals — hold this line

    • Don’t generate platform code. The scope creep that kills these systems. The design system would end up maintaining Swift and Kotlin codegen it cannot competently review, forever.
    • Don’t model layout mechanism. Direction, order, alignment, and sizing are design decisions and belong in the contract. HStack vs. Row vs. flexbox is syntax and does not.
    • Don’t build a token pipeline. Reference the library, validate against it, resolve symbol names. Nothing more.
    • Don’t derive the contract from React. Extraction bakes DOM events, className, and flexbox assumptions into the one artifact that must not have them.
    • Don’t let prose into the artifact. If a note is load-bearing, that is a schema bug. Prose belongs in docs.
